# 数据导入管道

> 状态：active · 最后更新 2026-09-01
> P0 已完成，P1 待办。

## 定位

**项目代码，但不是服务代码。** 它不常驻、不响应请求，但必须长期存在于仓库里：

- 题库会更新（勘误、补题）→ 要重跑
- AI 结果要能重新生成（换模型、改提示词）→ 要重跑
- **第二个题库进来时整套管道复用** → 这是它最重要的价值

语言用 **Python**：单向 ETL，不需要与后端共享类型；PDF/文本处理生态压倒性优势。

## 三段解耦

```
PDF ──[① 解析]──> questions.json ──[② AI 富化]──> enriched.json ──[③ 导入]──> DB
                       ↑                              ↑
                可 review / 可进 git / 可 diff       同上
```

**产出稳定的中间格式，不直接写数据库。** 好处：

- 解析出错能直接看中间产物，不用查数据库
- AI 结果进 git，**版本可追溯**（改提示词重跑，diff 一眼看出哪些题的裁决变了）
- 换数据库不用改解析器
- **上线不需要迁移数据库**，拿 `enriched.json` 对生产库重跑 ③ 即可

这是「接口 > 实现」在数据管道上的应用。

## 素材收件区（inbox）

**原始素材（PDF 等）不进仓库** —— 体积大 + 版权。约定如下：

```
$MELETE_INBOX/<bank-slug>/<任意文件名>        默认 ~/melete-inbox/
          ↓  python3 pipeline/core/ingest.py <bank-slug>
data/<bank-slug>/questions.json               结构化产物（进 git）
data/<bank-slug>/source.yaml                  素材登记单（进 git，仅元数据）
```

流程：

1. 素材长期存放在**你自己的磁盘**上，仓库不管
2. 要导入时，复制到收件区里对应的题库子目录
3. 跑 `ingest.py`
4. 处理完，**由你自己**把素材拿走 —— **脚本不删除、不移动任何用户文件**

### 登记单（source.yaml）解决什么问题

素材拿走之后，仓库仍然知道：产物来自哪个文件（`filename` + `sha256` + `bytes`）、
什么时候导入的、用哪个 git 版本的解析器生成的、产出了多少题多少告警。

将来拿到新版素材，**比对 sha256 即可判断是不是同一份**，不用凭记忆。

### 题库自身的重复题可用来修复缺陷（2026-09-02）

`#868` 在源 PDF 里缺了选项 A（整题只有 B/C/D）。富化侧做题时发现
**`#889` 与它是同一道题**：题干相似度 0.9927、B/C/D 逐字相同、标注与投票均为 B。
于是用 `#889` 的 A 补全了 `#868`。

这不是「编造数据」，是**拿题库自己的另一份副本修它** —— 修复在解析器层
（`DUPLICATE_REPAIRS` 表），重跑 ingest 依然生效，并记入 warnings 保持可追溯。

> 启示：题库里的重复题通常被视为噪声，但当其中一份有缺陷时，
> 另一份就是**现成的、来源可信的修复材料**。换题库时值得先做一次重复题检测。

### 已修的 bug（换题库时容易重犯）

0. **题头只认中文「问题 #N」**，8 道英文题头「Question #N」的题被整题吞进前一题
   （表征：#252 投票分布 200%）。更危险的是当时用**中文 grep 去「验证」这些题不存在**
   —— 验证工具与解析器共享同一盲区，得出了「题库自身缺号」的错误结论。
   教训：验证一个工具的盲区，必须用**不同构造**的手段（这次靠的是投票和异常这个
   独立信号回溯）。已加哨兵：`vote_distribution_sum_gt_100`

1. `ANS_LINE` 正则忘了 `re.M`，导致 `(.*)$` 只在「正确答案」恰为最后一行时匹配
   → `bank_label` 只抽出 104/1011 条
2. 西里尔字母混入拉丁选项字母，需 `str.maketrans` 归一

### 「时效性漂移」：题库里最隐蔽的一类错误

**正确答案会随 AWS 特性迭代而改变**，而题库标注与社区投票都停在成文那一年。
这类错误无法靠解析器检测，只能靠富化侧的知识判断。已确认的清单：

| 变更 | 时间 | 影响的题 |
|---|---|---|
| DMS Serverless GA | 2023 | SAA #948（题库+社区都选「多可用区」，那是可用性方案，不是容量方案） |
| AWS 托管 KMS 密钥轮换 3 年 → 1 年 | 2022-05 | SAA #942 |
| Organizations 声明式策略支持 EBS 默认加密 | 2024-12 | SAA #419 |
| S3 默认加密 SSE-S3 | 2023-01 | — |
| S3 新桶默认禁用 ACL | 2023-04 | — |
| NLB 支持安全组 | 2023-08 | — |

处理约定：**按题目成文年代的事实判**，但在 notes 里同时写明现行行为 ——
两种口径都给，学习者才知道这题为什么有争议。

### 反对「题库 + 社区一致意见」的取舍标准

极少数题两个来源都错（SAA 实例：#948 DMS Serverless、#950 Transit Gateway 加密）。
富化侧确立的标准，已采纳为纪律：

> 判错一道题，学习者只是丢一分；
> 跟着错答案走，学习者会把错误的 AWS 事实带进真实架构工作。
> **后者代价大得多。**

所以按技术事实判，`confidence` 给 medium，并在 notes 里标注「建议人工复核」。

### 两条方法论（2026-09-02，与富化侧协作中沉淀）

- **校验解析器的手段不能与解析器共享同一套模式。** 中文 grep 验证中文正则 =
  盲区里互相印证。打破盲区靠的是**独立信号**（这次是投票和 200% 这个数值异常）。
  富化侧的对应纪律：凡「数据自洽但数值不合常理」一律上报，不自行消化
- **社区共识度取首选项的原始百分比，不做归一化。** 源站 的 distribution
  是长尾截断的（合计常在 79-89%），A(45%)/B(20%) 归一化会虚标成 69% 的高共识，
  把真正的低共识题漏出筛网

### 系统性译文缺陷：三例撞词（本素材最主要的语义缺陷模式）

结构层脏点（缺选项、错切、图片丢失）靠解析器检测即可；**语义层的译文撞词只有精读才能发现**，
且危害递增。三例都由富化侧在做题时撞见、再回头做全库检索定性：

| # | 英文原词 | 误译成 | 危害 | 检测 |
|---|---|---|---|---|
| 1 | Spot Instances | 按需实例（撞 On-Demand） | 同题选项失去区分度，#128 四个选项两两相同 | `duplicate_choice_bodies_*` |
| 2 | Aurora Serverless | 按需 Aurora（再撞 On-Demand） | #511 社区 59/41 分裂 —— 读中译版看不出 C 是 Serverless | `suspect_serverless_mistranslation_*` |
| 3 | provisioned / reserved concurrency | 译法四选一、且互相串用 | **跨题矛盾**：#516 教「预留并发不消冷启动」，#597 却用它消冷启动 | `lambda_concurrency_term_ambiguous_*` |
| 4 | **专有名词被拆词直译** | Babelfish→「Babel shell」、Redshift→「红移」、Snowball→「雪球」 | 产品名失真，无法与真实 AWS 服务对应 | `product_name_mistranslated_*`（7 道） |

前三例是**撞词**（不同概念共享一个中文词），第四例性质不同 ——
是**专有名词被当普通词组翻译**。它由富化侧做题时撞见（#886 的「Babel shell」），
全库扫描后又找出 6 处。这类的识别只能靠对照真实产品名清单，规则化程度低。

第三例危害最大：前两例是单点误译，它是**互相矛盾的判据** —— 会摧毁学习者刚建立的正确认知。
完整映射表与逐题处理约定见 `pipeline/banks/aws-saa-c03/enrich_spec.md`。

**换题库时的启示**：机翻题库的术语撞词集中在「同一英文概念有多个中文习惯译法」
与「不同英文概念共享一个中文词」两类，值得在 P0 阶段就为该领域的核心术语建一张
对照表并全库检索，而不是等做题时逐个撞见。

### 文本层确定性修复（2026-09-02，SAP-C02 引入）

解析器只修「信息损失可无歧义还原」的缺陷，修好的登记进 `repairs` 字段（不是 `warnings`：
已修好的不需要人看，465 题的登记会淹没真告警）。目前两类：

| 缺陷 | 成因 | 规模 | 修法 | 位置 |
|---|---|---|---|---|
| 缩写句点被吞：`VPC. Create → VPCreate` | 源站 抓取把正文里「字母. 」当选项标签剥掉；末字母落 A–F 的缩写中招 | 34 题 | 缩写表 `{VP→VPC, AL→ALB, NL→NLB, MF→MFA}` × 后接大写动词 | `banks/aws-sap-c02/parse.py`（源格式特有） |
| 连字丢失：`Configure → Con gure`、`file → le` | pdftotext 抽取；PDF 字体缺 ToUnicode，fi/fl/ffi/ffl 变成一个空格 | 76.7% 的题 | **封闭词表**还原，词中形态先于词首形态 | `core/textrepair.py`（任何英文题库都会遇到） |

三条经验：

- **封闭词表 > 系统词典**：词典法会把 `a n` 还原成 flan、把 `sts:AssumeRole` 的 sts 还原成 fists。
  词表从语料统计生成、逐词肉眼核过，产物不随机器上的词典版本变。新题库出现表外词：先统计，核过再加
- **词中形态不能用 `re.sub`**：`SNS noti cation` 会先配到 `SNS noti`，失败后扫描指针已越过 `noti`。
  要手动推进，失败时只前进到右残片开头
- **验收标准是「文本有改动的题 == 登记了修复的题」**，且 claims / warnings / kind / pick 全部不变 ——
  这一条等式证明零误伤，比看样本可靠
- `IPSet` 是 WAF 真实资源名，长得像被吞的 `IP. Set`，必须不在缩写表里。同类白名单需求出现时在此登记

⚠ 重跑解析器会改题面 → 富化侧的 fp 指纹随之变化，须通知富化会话 `git pull` 后重新 `next`。

## ② AI 富化（P1，待办）

### 一次调用产出全部，不分三遍

三种标签 + 答案裁决 + 解析**必须在同一次调用里完成**。分三遍跑 1011 道题 = 三倍成本和三倍延迟，且三次结果可能互相矛盾。

### 输出契约

每片一个文件，`items` 数组的元素形如：

```json
{
  "no": 26,
  "verdict": "B",
  "confidence": "high",
  "reasoning": "为什么是 B；以及题库标注的 A 错在哪",
  "explanation": "完整解析，面向学习者",
  "domain": 3,
  "services": ["S3", "CloudFront"],
  "concepts": ["cache/cdn"]
}
```

- `verdict` 必须是选项中存在的字母，升序不重复，长度 == `pick`
- `concepts` 为 **kebab-case 通用架构概念**，优先取 `enrich_spec.json` 的 51 个种子词
- `domain` 为 SAA-C03 官方 4 域之一
- 题目本身有缺陷时（缺选项等）`verdict` 留空、`data_issue` 写明原因，**不要硬编答案**

> **concept 词表决策（2026-09-01）**：曾考虑限定在 atlantis 现有路径集合内，已否决 ——
> atlantis 那 114 篇主题是 Linux / K8s / 基建，AWS 架构概念覆盖很薄，
> 强制限定会导致大量题 `concepts` 为空，第三个标签维度形同虚设。
> concept 按设计是**全局共享**的，atlantis 只是它的消费方之一，不该反过来当约束源。
> 代价：P5 迁入 atlantis 时需要一轮人工归并。

### 执行方式：Claude Code 订阅额度 + 分片续跑

~~Claude Batches API~~ —— **已否决**。评估过：分层跑（Sonnet 低档 + Opus 高档）
约 $16，其中 thinking token 是成本主导项。但用户的 Max 订阅额度本就闲置，
这笔钱没有花的理由。

改为**由 Claude Code 会话逐片生成**。代价是跨多次限额周期、可能换会话，
所以 `pipeline/core/enrich.py` 的核心职责是**让中断可恢复**：

```
data/<bank>/enriched/NNNN-NNNN.json     一片 25 题，41 片
```

- **分片文件存在即完成** —— 不维护单独的进度清单。
  manifest 与实际文件不同步是这类流程最经典的坑，直接不给它机会
- 每片独立校验，坏片删掉重跑，不影响其他片
- 换会话接手：读 `pipeline/banks/<bank>/enrich_spec.md` + 跑 `status`，立刻知道进度

```bash
enrich.py status <bank>          # 进度
enrich.py next   <bank>          # 取下一片题目（喂给解答会话）
enrich.py write  <bank> <file>   # 从 Python 字面量写入分片（推荐）
enrich.py check  <bank>          # 校验
enrich.py merge  <bank>          # 合并 → enriched.json（不进 git，可重建）
```

**为什么有 `write`**：富化侧直接用 heredoc 手写 JSON 三次踩坑（裸换行 ×2、
非法转义 ×1）—— JSON 转义规则对「含 markdown 表格与中文标点的长解析」太脆弱。
改用 Python 字面量后三引号里一切都是字面值，问题从根上消失；
且**写盘前先全量校验，一条不过整批不写**，坏数据不会留下半成品分片。

这是个值得记的通用教训：**当工具反复在同一处出错时，该改的是工具而不是使用纪律。**

同理还有一条门禁：`write` 要求每个 item 携带**题面指纹** `fp`（8 位哈希，
`next` 的输出里给出），对不上即整批拒写。它防的是「上下文被压缩后凭记忆写」——
2026-09-02 实发过一次，11 道题的选项描述是脑补的。

设计要点：**门禁必须是「只有接触过真实数据才能通过」的**。曾评估「抄题干前 20 字」
的方案，实测 37 题撞车且撞的正是同类题（都以「一家公司在 EC2 上运行…」开头）——
那种校验挡不住最容易记混的情况。哈希零撞车且无法凭记忆构造。

题库特有的约束（考纲域 / concept 种子 / 服务命名）在
`pipeline/banks/<bank>/enrich_spec.json`，**core 零题库特有逻辑**。

### 「时效性漂移」：题库里最隐蔽的一类错误

**正确答案会随 AWS 特性迭代而改变**，而题库标注与社区投票都停在成文那一年。
这类错误无法靠解析器检测，只能靠富化侧的知识判断。已确认的清单：

| 变更 | 时间 | 影响的题 |
|---|---|---|
| DMS Serverless GA | 2023 | SAA #948（题库+社区都选「多可用区」，那是可用性方案，不是容量方案） |
| AWS 托管 KMS 密钥轮换 3 年 → 1 年 | 2022-05 | SAA #942 |
| Organizations 声明式策略支持 EBS 默认加密 | 2024-12 | SAA #419 |
| S3 默认加密 SSE-S3 | 2023-01 | — |
| S3 新桶默认禁用 ACL | 2023-04 | — |
| NLB 支持安全组 | 2023-08 | — |

处理约定：**按题目成文年代的事实判**，但在 notes 里同时写明现行行为 ——
两种口径都给，学习者才知道这题为什么有争议。

### 反对「题库 + 社区一致意见」的取舍标准

极少数题两个来源都错（SAA 实例：#948 DMS Serverless、#950 Transit Gateway 加密）。
富化侧确立的标准，已采纳为纪律：

> 判错一道题，学习者只是丢一分；
> 跟着错答案走，学习者会把错误的 AWS 事实带进真实架构工作。
> **后者代价大得多。**

所以按技术事实判，`confidence` 给 medium，并在 notes 里标注「建议人工复核」。

### 两条方法论（2026-09-02，与富化侧协作中沉淀）

- **校验解析器的手段不能与解析器共享同一套模式。** 中文 grep 验证中文正则 =
  盲区里互相印证。打破盲区靠的是**独立信号**（这次是投票和 200% 这个数值异常）。
  富化侧的对应纪律：凡「数据自洽但数值不合常理」一律上报，不自行消化
- **社区共识度取首选项的原始百分比，不做归一化。** 源站 的 distribution
  是长尾截断的（合计常在 79-89%），A(45%)/B(20%) 归一化会虚标成 69% 的高共识，
  把真正的低共识题漏出筛网

### 系统性译文缺陷：三例撞词（本素材最主要的语义缺陷模式）

结构层脏点（缺选项、错切、图片丢失）靠解析器检测即可；**语义层的译文撞词只有精读才能发现**，
且危害递增。三例都由富化侧在做题时撞见、再回头做全库检索定性：

| # | 英文原词 | 误译成 | 危害 | 检测 |
|---|---|---|---|---|
| 1 | Spot Instances | 按需实例（撞 On-Demand） | 同题选项失去区分度，#128 四个选项两两相同 | `duplicate_choice_bodies_*` |
| 2 | Aurora Serverless | 按需 Aurora（再撞 On-Demand） | #511 社区 59/41 分裂 —— 读中译版看不出 C 是 Serverless | `suspect_serverless_mistranslation_*` |
| 3 | provisioned / reserved concurrency | 译法四选一、且互相串用 | **跨题矛盾**：#516 教「预留并发不消冷启动」，#597 却用它消冷启动 | `lambda_concurrency_term_ambiguous_*` |
| 4 | **专有名词被拆词直译** | Babelfish→「Babel shell」、Redshift→「红移」、Snowball→「雪球」 | 产品名失真，无法与真实 AWS 服务对应 | `product_name_mistranslated_*`（7 道） |

前三例是**撞词**（不同概念共享一个中文词），第四例性质不同 ——
是**专有名词被当普通词组翻译**。它由富化侧做题时撞见（#886 的「Babel shell」），
全库扫描后又找出 6 处。这类的识别只能靠对照真实产品名清单，规则化程度低。

第三例危害最大：前两例是单点误译，它是**互相矛盾的判据** —— 会摧毁学习者刚建立的正确认知。
完整映射表与逐题处理约定见 `pipeline/banks/aws-saa-c03/enrich_spec.md`。

**换题库时的启示**：机翻题库的术语撞词集中在「同一英文概念有多个中文习惯译法」
与「不同英文概念共享一个中文词」两类，值得在 P0 阶段就为该领域的核心术语建一张
对照表并全库检索，而不是等做题时逐个撞见。

### 素材对照

| | SAA-C03 中文版 | SAP-C02 英文版 |
|---|---|---|
| 题量 | 1019 | 529 |
| 零告警率 | 94.8% | **98.1%** |
| 题号缺失 | 曾漏抓 8 道 | **0** |
| 社区投票覆盖 | 88% | **99.1%** |

**分歧率 54.6% 是个重要发现**：Professional 级题目的标注答案更不可靠 ——

在 SAP 上比在 SAA 上更有价值。

### 解析器的唯一新逻辑：剥离社区讨论

英文版每题后跟几十条评论，而**评论里也有 `A.` 开头的行**
（如「A. Correct answer. Source: ...」），不切干净会被当成选项。

判据：切到第一个「用户名 + 徽章/相对时间」行为止
（`Highly Voted` / `Most Recent` / `N years ago`）。实测 529 题全部切对。

其余四处只是换字符串：题头 `Question #N`、答案行 `Correct Answer:`、
投票区 `Community vote distribution` + `A (86%)`、多选 `(Choose two)`。

### 10 道告警题：全部核实为素材脏点，非解析 bug

- `#6` B≡C、D≡E —— 选项后跟的 **JSON 策略块未抓到**（同 SAA 的 #96）
- `#200` 标签 `A B B C D E` —— **源文本里就印了两个 `B.`**（`F` 被印成 `B`，同 SAA 的 #125 把 `E` 印成 `D`）
- `#483` 缺选项 A —— 同 SAA 的 #868，已由「缺 A 退而认首个字母」的逻辑救回 3 个可用选项
- 其余为多选题只标了单个答案等题库自身问题

## ⭐ 换题库检查清单（SAA-C03 全量富化后沉淀）

1019 道题跑完，63 道被标记（6 blocking + 57 advisory）。按**换新题库时应逐项排查的顺序**：

### 检查项 1：内嵌代码块/策略缺失 —— 解析器完全查不出，且 100% 不可裁决

PDF 里以**图片形式**嵌入的 JSON/策略/架构图，文本层为空。
SAA 实例：#96 #253（阻断）· #429 #494（可由选项反推）。

判据：`stem 以冒号或「以下」结尾但后续无内容`。已实装
`stem_ends_with_colon_missing_block` 与 `stem_references_missing_block`。
**换题库第一件事就跑这个** —— 这类题富化侧只能标 data_issue，无法裁决。

### 检查项 2：stem 末行丢失

SAA 的 #460/#467/#473 是**同一分片内连续三道**都丢了设问句 ——
强烈提示解析器在某种排版下会吃掉最后一行。
判据：`stem 不以问号结尾`（已实装 `stem_missing_question`，SAA 命中 6 道）。
**在新题库上要专门验证这个比例**，异常升高说明排版触发了同一个 bug。

### 检查项 3：跨题串行

上一题的选项混入本题 stem。SAA 仅 #775 一例，但它意味着**分栏排版下存在串行风险**。
建议加检测：`stem 首行与上一题任一选项高相似度`。

### 检查项 4：选项文本截断

`选项以冒号结尾`是可规则化的截断信号（SAA #980）。

### 检查项 5：投票分布合计异常

`distribution 合计 ≠ 100%`。它不影响裁决，但**会污染「低共识题」的统计口径**。
已实装 `vote_distribution_sum_gt_105`（阈值留 5% 舍入余量）。

### 检查项 6：四类译文缺陷 —— 中译题库必查

见下方「系统性译文缺陷」一节。**其中第 3 类（跨题矛盾）无法靠单题检测发现，
必须做全库的「同一英文术语的中译一致性」比对** —— 这是本轮最重要的方法论发现。

> 结论：**能拿到英文原版就别用中译版**。SAP-C02 已据此选用英文原版。

### 检查项 7：时效性事实 —— 富化产物有保质期

**这类题在任何题库里都会随时间增加。** 涉及「上限值 / 默认行为 / 产品是否存在」
的判据应当**每年复核一次**。已知的 9 条变更：

| 变更 | 时间 | SAA 受影响题 |
|---|---|---|
| DMS Serverless GA | 2023 | #948 |
| AWS 托管 KMS 密钥轮换 3年→1年 | 2022-05 | #942 |
| S3 默认加密 SSE-S3 | 2023-01 | — |
| S3 新桶默认禁用 ACL | 2023-04 | — |
| NLB 支持安全组 | 2023-08 | — |
| Organizations 声明式策略下发 EBS 加密 | 2024-12 | #419 |
| **Scheduled RI 停售** | — | #1013 |
| **HTTP API 不支持资源策略**（那是 REST API 的） | — | #1019 |
| **Aurora 无 Oracle 兼容版** | — | #978 |

### 检查项 8：medium 置信度的触发规则

`共识 <60% → medium` 实测触发 47 道，但最终给了 72 道 medium。
多出的来自「双来源 100% 一致但裁决相反」与「技术上有真实边界模糊」。
**规则应修正为**：共识 <60% **或** 裁决与两个来源都不一致 → medium。

## 换题库时要做什么

1. 新建 `pipeline/banks/<slug>/parse.py`，输出同一份 `questions.json` 契约
2. `pipeline/core/` 的 ② ③ 段**不需要改**
3. 题库特有的 `domain` 标签定义写进 `bank.meta`
4. `concept` 标签是全局的，新题库会自动与既有题目产生关联
