# 删除账号：用户在应用内删掉自己的账号与全部数据

> 状态：**草案，待用户裁决**（2026-10-24）· 裁决后落到 `docs/tasks/active/tracker.md` 的 P9 裁决表
> 由头：iOS 上架。App Store 审核指南 5.1.1(v)：支持创建账号的应用，必须在应用内提供删除账号。
> 现契约 36 个端点里没有删除账号；iOS 仓两份设计文档都把它标为「缺这个必被拒」。

## 0. 一句话

`DELETE /me`：当前用户的账号与全部数据**立即、不可逆**地删掉；所有登录会话吊销；
网页与 iOS 删完回到登录页。再次登录 = 从零开始的新账号。

## 1. Apple 的硬要求（设计边界）

| 要求 | 本设计怎么满足 |
|---|---|
| 必须能在**应用内发起** | 「我的」页底部的入口（网页 · iOS 同位置） |
| 必须删**整个账号记录与关联个人数据**，只停用不算 | 用户行与全部学习记录一起删（§3 清单） |
| 处理可以花时间，但要告知多久、完成要确认 | 同步完成，响应即确认，不需要「处理中」状态 |
| 法律要求保留的要说明 | 没有法律保留项；**备份里会留存一段时间**（§6）要写进隐私政策 |
| 可以加验证身份 / 确认意图的步骤，但不能刻意为难 | 两步确认（§5），不要求重新登录 |
| 用 Sign in with Apple 的要吊销其令牌 | 不适用：登录走第三方账号中心，没有 Sign in with Apple |

## 2. 待裁决项（背景 · 影响 · 推荐）

### ① 删除语义

**背景**：Apple 只要求「删掉」，没规定立即还是延迟。`users` 表已有 `deleted_at` 列（所有查询都带 `deleted_at IS NULL`），
软删的地基现成；但没有任何定时任务基础设施，宽限期需要新加一个会动的零件。

| 候选 | 会发生什么 |
|---|---|
| **a 立即硬删**（推荐） | 一个事务里删光 §3 的全部行。最简单，向审核员一句话说清；代价是**误点不可挽回**，靠两步确认挡 |
| b 软删 + 宽限期（如 30 天） | 标 `deleted_at`，期内再登录即恢复，到期由定时任务物理删除。多：定时任务（CronJob 或进程内 ticker）、恢复流程、「已计划删除」的界面状态、隐私政策要写宽限期 |
| c 匿名化保留作答 | 把 `attempt` 的 `user_id` 换成墓碑 id 留给将来的题目难度统计。现在没有任何跨用户统计在用这些数据；且「个人数据」的边界要自己论证 |

**推荐 a**。等有真实用户基数、出现「误删求恢复」的案例再考虑 b；c 等真有题目统计需求再说。

### ② 已签发的 access token 窗口

**背景**：access token 是无状态 JWT，有效 1 小时；认证中间件只验签不查库。账号状态只在 **refresh 时**复查
（模块 7.7）。⇒ 删完账号后，还握着未过期 access token 的客户端在最长 1 小时内仍能通过认证，
对不存在的 `user_id` 写 `attempt`（表间没有外键，插得进去）—— 变成孤儿行。**账号状态的其他变化（停用等）走的是同一条路，也要到下次 refresh 才生效。**

| 候选 | 会发生什么 |
|---|---|
| a 接受窗口 | 零改动；孤儿行要另写清理；封禁延迟 1 小时 |
| **b 中间件每请求复查账号状态，进程内缓存 30–60 秒**（推荐） | 删除 / 封禁最多 60 秒后全站生效；每请求多一次按主键查 `users`（缓存命中时为零）。两副本各自缓存，上限仍是 60 秒。标准做法（无状态 JWT + 吊销复查） |
| c 把 access TTL 从 1 小时缩到 10 分钟 | 窗口缩小但不消失；refresh 流量 ×6；网页与 iOS 的刷新逻辑已有，不用改 |

**推荐 b**。它顺手把「封禁即时生效」也修了；可以作为独立的小 PR 先上。

### ③ 确认方式

**背景**：Apple 允许验证身份（邮件 / 短信验证码），也允许只确认意图；但「刻意为难」会被拒。
我们的真实用户没有本地密码、邮箱只是上游带来的（没验证过），发信通道也只有 log 型。

| 候选 | 会发生什么 |
|---|---|
| **a 客户端两步确认，服务端不再验身份**（推荐） | 第一步说明后果（§5 文案），第二步确认按钮；服务端只认有效 access token。丢手机的人能删你账号 —— 但他本来就能看、能改、能登出，删除不是更高的权限 |
| b 服务端要求「新鲜」令牌（签发 ≤ 5 分钟） | 要先解决「换账号登录」那条待办（`oidcrp` 不能传 `prompt`），否则强制重登会被上游静默登回；多一条特例判断 |
| c 邮件验证码 | 没有可靠发信通道，第三方邮箱也未验证；对纯第三方登录用户不成立 |

**推荐 a**。

### ④ 契约形状

| 候选 | 说明 |
|---|---|
| **`DELETE /me`**（推荐） | REST 语义：删掉「我」这个资源；与 `/me/*` 一族同在；⛔ 不在 `/auth/` 下，不进 `PasswordRoutes` 隐藏清单（它对所有用户都开），也不触发 `/auth/` 端点归类测试 |
| `POST /me/delete` | 动词式；有的代理对 DELETE 带体不友好，但我们不带体 |

响应 `204 No Content`；401 = 令牌无效（含 ② b 下「账号已不存在」）。幂等：同一令牌重放在 ② a 下再返回 204。

### ⑤ 前置：localauth 阶段 6（删旧表）先做

**背景**：生产的旧 `account` 表里还有 3 行（含两位真实用户的第三方 `sub`），代码已不读它。删除账号若不管它，用户删完后旧表里仍留一行他的标识。

| 候选 | 会发生什么 |
|---|---|
| **a 先做阶段 6：DROP `account` / `account_session`**（推荐） | dev 自由；生产一次 DDL 要批。删除账号的代码从此不用知道旧表 |
| b 删除账号时顺带清旧表的行 | 代码里要写进两张马上要退役的表名；阶段 6 做完还得删这段 |

**推荐 a**，与本功能同一次发布（先 DDL 后镜像）。

## 3. 删什么（数据清单）

一个事务，顺序无关（没有外键）：

| 表 | 条件 | 备注 |
|---|---|---|
| `attempt` | `user_id = ?` | 学习记录 |
| `card` | `user_id = ?` | FSRS 卡片 |
| `bookmark` | `user_id = ?` | 书签 |
| `user_sessions` | `user_id = ?` | 先经 `SessionGuard.RevokeAll` 吊销（写审计），再物理删 |
| `user_permissions` | `user_id = ?`；另 `granted_by = ?` 的行置 NULL | 档位；别人的「由谁授予」不留悬空 id |
| `identities` | `user_id = ?` | ⭐ 删了它，再登录才会建新账号而不是登回旧 id |
| `verification_tokens` | `subject = <userID>` | 只有本地密码账号会有 |
| `login_failures` | `scope='account' AND fail_key=<username>` | 只有本地密码账号会有 |
| `users` | `id = ?` | 最后删 |

不碰：内容侧全部表（`bank` / `question` / `term` …）。旧 `account` / `account_session`：见 ⑤。

## 4. 代码结构

```
internal/account/deletion.go     Deleter：编排 —— 开事务 → 逐个领域的 Purger → 删 users → 审计
internal/account/repository.go   账号自己的行（users / identities / user_permissions / verification_tokens / login_failures）
internal/study/purge.go          学习侧的行（attempt / card / bookmark）—— 实现 account.UserPurger
internal/auth/service.go         DeleteAccount(ctx, userID)：RevokeAll 会话 → Deleter.Delete
internal/httpapi/me.go           DELETE /me → 204
```

**为什么用「每个领域自己清自己的行」而不是一段 SQL 删到底**：学习侧的表名不该出现在账号包里（高内聚）；
将来多一个领域（如 P5 的笔记 / 收藏文章），只需多实现一个 `UserPurger` 并注册，删除流程一行不改（开闭）。
代价是多一个接口、多几个文件 —— 换来边界清楚。备选「一段 SQL」更短，但账号包要认识全库的表。

```go
// account.UserPurger —— 某个领域在「用户被删除」时清掉自己名下的行。全部在同一个事务里。
type UserPurger interface {
    PurgeUser(ctx context.Context, tx *sqlx.Tx, userID string) (rows int64, err error)
}
```

审计：一条结构化日志 `account.deleted`，带不透明的用户 id 与各表删除行数。⛔ 不带邮箱 / 显示名。

## 5. 两端的入口与文案

**位置**：「我的」页最底部，登出按钮下方；灰字文本按钮「删除账号」，⛔ 不做成实底（这一页唯一的实底是登出）。

**第一步（说明）**：
> 删除账号会立即、永久地删掉：你的学习记录（作答 · 复习卡 · 书签）、题库选择、登录设备。
> 第三方账号本身不受影响；之后再用它登录，会得到一个全新的空账号。
> 备份中的副本会在 30 天内自动过期。

**第二步**：确认按钮「删除账号」+ 取消。删完回到登录页，顶部一条「账号已删除」。

**网页**：浏览器拿不到 access token（在 httpOnly cookie 里），所以经 BFF：`POST /auth/delete` 路由 → 调 API `DELETE /me` → 清 cookie → 第三方账号中心 `end_session` → 回首页（登录壳）。与现有 `/auth/logout` 路由同一套收尾。
**iOS**：直接调 `DELETE /me` → 清 Keychain → 回登录页。契约同步（重新生成 Client）后由 iOS 会话实现。

## 6. 盲点与边界（不是待裁决，但要知道）

- **再登录 = 新账号**：登录只走第三方账号中心、首次登录自动注册。删完后用户再点「登录」就会得到一个空账号 —— 这是设计结果，写进第一步文案。⚠️ 上游会话可能仍在（「换账号登录」那条待办），但建新账号仍需用户**主动点登录**，不会静默发生。
- **第三方账号中心与上游不受影响**：我们只删自己这边；隐私政策要写明。
- **备份**：生产库每日导出保留 30 天 ⇒ 删除后的数据在备份中最多存在 30 天。Apple 要求告知保留情况 ⇒ 写进文案与隐私政策。
- **日志**：审计与访问日志只含不透明 id，不含邮箱 / 显示名。
- **admin 删别人**：不做。#28 的原则：超级用户直接操作数据库。
- **最后一个 admin 删自己**：允许。admin 由超级用户重新授予（#28）。
- **删除期间的并发写**：事务内删；② b 之后新请求 60 秒内被拒。② a 下可能产生孤儿行，另需清理。
- **测试**：集成测试（`MELETE_TEST_DSN`）—— 建用户 + 各表各一行 → 删 → 各表为零 → 用同一个第三方 `sub` 再建，拿到的是**新 id**。

## 7. 不做的

数据导出（GDPR 可携带权）—— Apple 不要求；将来有欧洲用户再议。
